# Flowbind v0.1 provider boundary

Flowanalyst exports ABI requirements as facts rather than making the provider
choice itself. Each requirement contains:

```text
contract, library, convention, symbol, effect
```

Flowbind verifies `library` and `symbol` through the host dynamic loader. It
also validates the v0.1 C signature family and reports the host sizes of the
ABI carriers. It does not execute code or lower calls. Therefore:

```text
binding ready = provider found + supported signature family
binding ready ≠ call safe ≠ lowered
```

The first live probe uses `std/abi/libc.flow` and checks `libc.so.6` symbols
such as `strlen`, `abs`, `labs`, and `puts`. The report records that execution
was not performed.

The next boundaries are deliberately separate:

1. provider identity and search policy;
2. ABI signature/layout verification;
3. capability and effect authorization;
4. call lowering;
5. runtime dispatch or direct linkage.

## Capability policy

Flowbind denies external requirements unless an exact grant exists:

```text
allow LIBRARY SYMBOL CONVENTION EFFECT
```

For example:

```text
allow libc.so.6 strlen c pure
allow libc.so.6 puts c io
```

The grant must match all four fields. This prevents a symbol being authorized
under a different library, calling convention, or effect classification.
