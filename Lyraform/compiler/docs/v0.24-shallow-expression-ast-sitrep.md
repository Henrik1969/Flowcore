## Current core development law

```text
First existence.
Then visibility.
Then population.
Then dependency.
```

The current v0.24 work follows this order deliberately.

We are not trying to finish the whole language at once. We are making each layer exist, become observable, become regression-guarded, and then deepen it safely.

## Architectural stack

Current conceptual stack:

```text
Lexer
    Here are the words/symbols.

TokenTree
    Here are the words/symbols grouped by source structure.

Flowmini AST
    Here is what the program says.

SymbolTable
    Here is the structural projection of names and scopes.

Semantic analysis
    Here are resolution, types, diagnostics, facts, and contracts.

Graph IR
    Here is the executable/source architecture as nodes, ports, wires.

Lowerer/runtime
    Here is how we actually make it run.
```

Important distinction:

```text
TokenTree remembers what the source looked like.
AST states what the source means.
```

## Current expression capabilities

The AST can now represent the following shallow expression structures.

### Calls

```flow
square(x)
```

Current AST meaning:

```text
call expression
    text = "square"
    child_expressions = argument expressions
```

### Unary expressions

```flow
-x
```

Current AST meaning:

```text
unary expression
    text = "-"
    child_expressions = operand expression
```

Important rule fixed during A3:

```text
leading "-" at expression start is unary
"-" after a left expression is binary
```

### Binary expressions

```flow
x + 1
```

Current AST meaning:

```text
binary expression
    text = operator
    child_expressions = lhs expression, rhs expression
```

This is still shallow. It does not yet implement precedence trees.

### Index expressions

```flow
arr[i]
```

Current AST meaning:

```text
index expression
    text = "arr"
    child_expressions = base expression, index expression
```

### Field access expressions

```flow
p.x
```

Current AST meaning:

```text
field_access expression
    text = "p.x"
    child_expressions = base expression
```

The field name is still preserved only in the shallow text representation.

### List literals

```flow
[1, 2, 3]
```

Current AST meaning:

```text
list_literal expression
    text = "["
    child_expressions = element expressions
```

### Record literals

```flow
{x: 10, y: 20}
```

Current AST meaning:

```text
record_literal expression
    text = "{"
    child_expressions = field value expressions
```

Field names are not yet modeled as structural AST payloads.

## Known limitation: shallow child nodes

Child expressions are currently created shallowly.

Example:

```flow
square(x + 1)
```

May produce:

```text
call square
    child = binary "+"
```

But the binary child may not yet recursively contain its own `x` and `1` children depending on the path that produced it.

Recursive population is future work.

## Known limitation: binary precedence

Current binary expression handling is shallow.

Example:

```flow
a + b * c
```

The current AST should not yet be trusted as a proper precedence tree.

Future expression parser work must define:

```text
operator precedence
operator associativity
grouping behavior
unary/binary interaction
call/index/field binding strength
literal nesting
```

## Known limitation: record literals

Current record literals expose value expressions only.

Example:

```flow
{x: 10, y: 20}
```

Current shallow meaning:

```text
record_literal
    children = 10, 20
```

Future model should likely include something like:

```text
RecordLiteralField
    name
    value_expression
    location
```

## Current main/target rule

v0.24 currently supports exactly one root `main` block.

Multiple root `main` blocks remain an error.

Future language direction is named targets:

```flow
program toolset

target cli {
    main {
        ...
    }
}

target daemon {
    main {
        ...
    }
}
```

Canon law:

```text
A Flowcore program is a shared semantic universe.

A target is a named projection of that universe into a buildable or runnable product.

A main block is the entrypoint of a target.

For v0.24, root programs support exactly one main block.

Future versions may support named target scopes, each owning exactly one main block.
```

This is documented in:

```text
docs/language/named-targets.md
```

## Recommended next roads

### Road C1: recursive expression population

Purpose:

```text
Make child expressions recursively populate their own children.
```

Examples:

```flow
square(x + 1)
arr[i + 1]
{x: square(a + b)}
[1, x + 2, square(y)]
```

Current shallow nodes should become nested expression graphs.

### Road C2: real expression parser / precedence

Purpose:

```text
Replace shallow operator splitting with a proper expression parser.
```

Needed features:

```text
operator precedence
operator associativity
parenthesized expressions
unary precedence
call/index/field binding strength
nested binary trees
```

### Road C3: record literal field payloads

Purpose:

```text
Represent record literal fields as named field/value structures.
```

Likely model:

```text
RecordLiteralField
    name
    value_expression
    location
```

### Road C4: type-reference deepening

Purpose:

```text
Turn type references into real AST structures.
```

Needed:

```text
generic types
array types
reference/pointer types if kept
qualified names
function types later if desired
```

Status: complete for the honest v0.24 source forms.

Implemented:

```text
canonical NamedTypeRef payloads with qualified-name segments
canonical GenericTypeRef payloads with recursive type arguments
canonical ArrayTypeRef payloads with element type and source extents
derived kind/text compatibility projections
bounded recursive population depth (64)
payload/projection validation in the AST golden gate
```

Deliberately deferred:

```text
pointer and reference source forms
function types
generic value arguments and their semantic classification
type-name resolution and type checking
```

ABI pointer-shaped contracts remain named semantic types. Pointer/reference
syntax must not be added until ownership, mutability, lifetime, aliasing, ABI,
and safety semantics have been designed explicitly.

### Road C5: statement deepening

Purpose:

```text
Give statements stronger expression ownership and richer structure.
```

Needed:

```text
let initializer expression
assignment value expression
if condition expression
while condition expression
return value expression
else blocks
flow statements if kept
```

Current status: active. Conditional ownership and explicit `ElseArm` are now
represented through arena-owned statement/block IDs and guarded by ordinary
else, else-if chain, final-else, nesting, and unbraced-rejection coverage.
C5a-C5f are complete. Statement kind and compatibility JSON fields are derived
from payloads; Let, Assignment, Placement, Return, If, and While own their
meaningful fields; and the obsolete shared optional-field scaffold is removed.
Completion of C5 does not close v0.24: every remaining canonical form in the
accepted-language matrix must still be represented without loss.

### Road C6: SymbolTable bridge

Purpose:

```text
Connect AST declarations to named facts/scopes/contracts.
```

Needed:

```text
program scope
function scope
block scope
record scope
future target scope
symbol declaration
symbol lookup
shadowing rules
duplicate definition checks
```

### Road C7: Graph IR bridge

Purpose:

```text
Lower meaningful AST into graph-shaped Flowcore IR.
```

Needed:

```text
nodes
ports
wires
activation rules
policy/capability metadata
diagnostics
```
