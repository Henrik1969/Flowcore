# Flowmini v0.25 SymbolTable Projection Status

## Activation boundary

Flowmini v0.24 is frozen at the annotated tag:

```text
flowmini-v0.24-frontend-border
```

That checkpoint proves that an independent process can consume the versioned
raw AST and SymbolTable export without linking Flowmini internals or reparsing
source. v0.25 begins deliberately from that passed border on:

```text
branch:     v25-symboltable-projection
directory:  Flowmini/flowmini_v25_symboltable_projection
```

The v0.24 implementation directory remains preserved. The v0.25 directory was
copied without build trees, runtime build output, test reports, or Python cache
artifacts.

## Canonical purpose

v0.25 matures the AST-to-SymbolTable projection as trustworthy input for
semantic analysis and independent downstream tools, and now participates in the
verified language chain through LLVM and native ELF output for selected profiles.

v0.25 owns:

- complete structural SymbolTable projection coverage for the canonical raw AST;
- explicit, stable-within-a-revision AST-to-symbol and AST-to-scope origins;
- source filename and imported-source provenance at the exported boundary;
- factual metadata completeness without semantic interpretation;
- expanded SymbolTable projection and frontend-consumer goldens;
- frontend bundle schema validation, determinism, and compatibility hardening;
- a documented entry contract for the later semantic-analysis stage.

v0.25 does not own:

- semantic type resolution or alias normalization;
- identifier legality, overload choice, mutability, or assignability checking;
- contract or refined-type satisfaction;
- ABI lowering;
- Graph IR;
- ModuleSpec replacement;
- general runtime lowering or execution redesign. Selected downstream profiles
  are implemented by the sibling Flowlower stage.

The binding law remains:

```text
Raw AST preserves source structure and spelling.
SymbolTable projection records factual structure and metadata.
Semantic analysis interprets those facts in Flowanalyst; later stages preserve
the resulting contracts rather than reparsing source.
```

## Independent consumers enabled by the border

The frontend bundle is a project boundary, not an invitation to absorb every
tool into Flowmini. It is intended to allow separately owned tools such as:

1. semantic checkers and linters;
2. documentation generators;
3. transpilers and alternate lowering experiments;
4. explainers and visualizers, including public-art renderings of program
   structure and flow.

These tools consume the versioned contract. They should not link private
Flowmini frontend implementation or reparse source to reconstruct omitted facts.

## First maturation questions

The first v0.25 development work should inventory, then decide one item at a
time:

- which canonical AST declarations or bindings still lack projected symbols;
- which factual fields exist in the AST but are absent from SymbolTable facts;
- whether every origin link identifies the most precise owning AST structure;
- which cross-run identity guarantees, if any, are required beyond the current
  stable-within-one-export rule;
- how schema evolution and compatibility rejection are versioned;
- what minimum projection contract the independent semantic checker requires.

Those questions governed the opening projection milestone. The current sibling
chain now consumes the export through Flowanalyst; new semantic rules remain
downstream contracts rather than frontend projection responsibilities.

## Current structural-origin maturity checkpoint

The first maturation audit advanced the bundle envelope to version 2 while
retaining `flowmini.ast.v2` and `symboltable.snapshot` version 1. Symbol and
scope origins now carry explicit entity kinds, structural roles, canonical AST
IDs where the arena owns one, and matching source locations. The independent
consumer validates these fields and builds reverse AST-to-symbol/scope lookup
without name guessing.
