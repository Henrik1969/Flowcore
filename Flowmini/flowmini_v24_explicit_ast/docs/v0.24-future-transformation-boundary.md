# Flowmini v0.24 — Future Transformation Boundary

Authority: binding boundary guidance for v0.24. Mentions of future completion
criteria or provider mechanisms remain provisional until separately approved.

## Purpose

Flowmini v0.24 is not implementing the future optimizer or Graph IR machinery.

Its job is to make the AST explicit and semantically reliable enough that those
later stages can be added without reinterpreting source syntax or rewriting the
AST around one backend.

This note records the constraints that the broader Flowcore transformation
architecture places on current v0.24 work.

The project-wide design is documented in:

```text
docs/architecture/compiler-transformation-revision-model.md
```

## Current law

```text
TokenTree remembers what the source looked like.
AST states what the source means.
```

v0.24 should continue deepening that boundary.

## What the v0.24 AST must preserve

The AST should make semantic roles explicit enough that later stages can reason
without consulting raw token spelling.

Current examples already moving in this direction include:

```text
explicit expression payloads
explicit type-reference payloads
return value ownership
typed-binding initializer ownership
assignment value ownership
if/while condition ownership
if-owned optional else branch
```

Future AST deepening should follow the same rule.

## What must not leak into the AST

The semantic AST should not become storage for decisions that belong to later
stages.

Do not encode target or optimizer preferences such as:

```text
x86_64 instruction selection
register choice
SIMD width
backend ABI details
scheduler decisions
prefer recursion/iteration/parallel execution
optimizer cost scores
target-specific lowering shortcuts
```

unless some future language semantic explicitly requires such a fact.

The AST should say what an operation is, not how a particular target should
execute it.

## Preparing for Graph IR

Graph IR begins only after the frontend semantic border: a complete raw AST,
lossless structural SymbolTable projection, and semantic
analysis/facts/contracts/diagnostics. The AST must be sufficiently canonical
that one structural fact does not have several competing authoritative
locations.

Temporary compatibility projections are acceptable during migration, but the
future Graph IR builder should consume canonical semantic ownership rather than
guess between legacy and new representations.

The gate into Graph IR must eventually include facts such as:

```text
names resolved
type references semantically validated
calls/identities resolved
flow relationships semantically valid
effects represented sufficiently for ordering decisions
source provenance retained
invalid programs rejected with structured diagnostics
```

The exact semantic-analysis completion list remains future design work.

Current `ModuleSpec`/FlowIR is a compatibility execution target below canonical
Graph IR. It is not the Graph IR model and must not define it.

Legacy direct node, wire, and policy syntax remains compatibility-only on the
current `parseModule()`/`ModuleSpec` path during v0.24. It does not require raw
AST nodes because canonical nodes, ports, wires, and policies belong to Graph
IR after semantic analysis.

Likewise, output is an ordinary call through a capability/provider function,
not a core `Print` statement kind. Existing `print value` spelling is
provisional compatibility syntax until it migrates to a call form.

Value placement is different and has a canonical AST ruling:

```text
expr -> ordinary_target
    PlacementStatement(value_expression, AssignableTarget)

expr -> return
    ReturnStatement(value_expression)
    source form: arrow placement
```

Return is control transfer, not storage, and is never an assignable target.
Later semantic analysis validates whether an `AssignableTarget` is legal.
AST-only assignment and return spellings do not silently satisfy accepted arrow
syntax coverage.

The v0.24 target taxonomy is deliberately closed:

```text
AssignableTarget =
    IdentifierTarget
  | FieldPathTarget
  | IndexedTarget
```

It mirrors accepted executable syntax and is not a generic expression target.
Future target forms require explicit new variants. Scope, mutability, type
compatibility, and assignability remain semantic-analysis responsibilities.

Payloads mirror `parseAssignableTarget()`:

```text
IdentifierTarget(name, location)
FieldPathTarget(base_identifier, ordered located field segments)
IndexedTarget(base_identifier, one-or-more index ExpressionIds)
```

Index components may reference expressions; the target node itself stays
closed over accepted l-value syntax.

Source spelling is explicit provenance metadata:

```text
PlacementStatement.source_form  = ArrowPlacement
ReturnStatement.source_form     = KeywordReturn | ArrowPlacement
AssignmentStatement.source_form = EqualsAssignment
```

These remain distinct semantic statement forms. Source-form metadata supports
diagnostics and provenance but does not redefine ownership or make return a
storage target.

### Typed statement payloads

C5 migrated `Statement` from a shared optional-field scaffold to location plus
a typed payload variant. Statement kind is derived from payload type. Each
payload owns only its meaningful semantic fields; kind strings, generic
expression-ID lists, and legacy JSON fields remain derived compatibility
projections.

The migration is staged: define payloads; derive projections; migrate
Let/Assignment/Return; migrate If/While/ElseArm/BlockId; add Placement; then
remove irrelevant scaffolding after all goldens cover the canonical payloads.

C5a-C5f are complete. Let, Assignment, Placement, Return, If, and While own
their meaningful data; direct ElseArm and BlockId structure is payload-owned;
statement kind and legacy JSON fields are derived and validator-checked; and
the obsolete shared optional fields have been removed. The placement golden
covers identifier, located field-path, indexed, and arrow-return forms.

## Identity and revision readiness

Future Flowcore IRs are intended to support stable entity identity and published
revisions such as:

```text
Node 42:r7
```

v0.24 does not need to retrofit revision machinery into every AST object now.

However, current decisions should avoid making stable identity impossible.

Where cross-reference, provenance, or later transformation history benefits
from stable identity, prefer opaque/stable IDs over raw memory identity.

The existing expression-pool index model is therefore architecturally useful:
semantic structures can refer to expressions without depending on object
addresses.

Whether those IDs later become revision-aware is a separate implementation
decision.

## Source provenance

Source location must continue to survive semantic deepening.

The long-term provenance chain should be able to relate:

```text
source
  -> AST
  -> Graph IR
  -> optimized Graph IR
  -> target IR
  -> artifact
```

v0.24 owns the first durable link in that chain.

## Default implementation versus future alternatives

Flowmini should implement one sane default path.

It does not need dynamic plugin loading, multiple AST engines, multiple graph
stores, or multiple optimization policies now.

What it must do is preserve boundaries so future providers can be substituted
without redefining semantics.

Therefore:

```text
default != definition
```

The current implementation is a prototype provider for the architecture, not
the permanent representation law.

## Immediate review rule for v0.24 changes

For every AST change ask:

```text
1. Does this make source meaning more explicit?

2. Can a future semantic/Graph IR stage consume this without reparsing source?

3. Does it preserve provenance needed for diagnostics?

4. Is this semantic fact represented canonically?

5. Are we accidentally encoding an optimizer, scheduler, runtime, or target
   preference into the AST?
```

If questions 1-4 are satisfied and question 5 is no, the change is aligned with
the future architecture.

## Current development consequence

Continue C5 AST stabilization.

Do not interrupt v0.24 to implement the future optimizer.

The value of this architecture checkpoint is that C5 and later semantic work can
now be judged against known downstream requirements before those requirements
become expensive implementation constraints.
