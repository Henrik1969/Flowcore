# Flowmini v0.24 Explicit AST Status

Status: active development branch  
Branch theme: explicit AST stabilization  
Implementation maturity: canonical expression/type-reference payloads, completed C5 typed statement payloads, and arena-owned statement/block structure; observable and regression-guarded

Authority: current-state evidence. Architectural laws linked from this report
are binding; incomplete-feature lists and gate counts describe this checkout
and must change when verified behavior changes.

Completed C5 evidence is summarized in
[the typed-statement sitrep](v0.24-c5-statement-payload-sitrep.md).

## Purpose of v0.24

The v0.24 Flowmini line exists to make the AST explicit and trustworthy.

Earlier work made lexer and TokenTree behavior observable. v0.24 moves the project toward a first-class AST layer.

The guiding distinction is:

```text
TokenTree remembers what the source looked like.
AST states what the source means.
```

Current architecture stack:

```text
Lexer
    Here are the words/symbols.

TokenTree
    Here are the words/symbols grouped by source structure.

Flowmini AST
    Here is what the program says.

SymbolTable
    Here is the structural projection of names and scopes.

Semantic analysis
    Here are resolution, types, diagnostics, facts, and contracts.

Graph IR
    Here is the executable/source architecture as nodes, ports, wires.

Lowerer/runtime
    Here is how we actually make it run.
```

## Current SymbolTable projection checkpoint

The `--dump-ast-symbols` path now projects source-unit, import, function,
parameter, record, field, refined type, ABI contract/type/struct/extern, main,
block, and local-binding structure from the explicit AST into SymbolTable. It
consumes the arena-owned expression, statement, and block representation,
including invariant expression IDs and direct else-if continuations, without
taking ownership away from the AST.

Eleven golden projection probes currently guard program and unit source kinds,
nested conditional scopes, type/declaration scopes, placement-bearing programs,
function signatures with present and absent return spelling,
initializer-bearing locals, recursive-expression programs, refined invariants,
and ordered ABI declarations. Projected symbols carry factual source metadata:
source-unit kind, declaration line/column, declared and return type spellings,
refined base/invariant spellings, and written ABI/extern clause spellings. No
ABI defaults are injected. Type strings are rendered from raw AST `TypeRef`
values without resolving aliases or canonical identities. The AST currently has no
source-file field, so projected declaration locations expose line/column while
the dump reports the unavailable file component as `<source>`.

This structural and factual projection satisfies the declared v0.24 raw
frontend/export border. Resolution, type checking, and derived semantic facts
remain deliberately later work.

## Independent frontend export checkpoint

`--dump-frontend-bundle` exports the versioned `flowmini.frontend_bundle` v1
envelope. It contains the current `flowmini.ast.v2` object, a generic
`symboltable.snapshot` v1 object, Flowmini-owned JSON Pointer sidecars linking
every symbol and non-global scope to canonical AST structure, source identity,
and the reserved diagnostics array.

The standard-library-only Python consumer validates the export without source
input, Flowmini headers, or Flowmini library linkage and emits a deterministic
lowering skeleton. The CMake-visible gate covers five goldens, one isolated
consumer run, and eleven negative attacks. These are structural origins, not
semantic use-to-symbol resolution.

## What the AST does not yet guarantee

The v0.24 AST is not yet a full semantic or executable language model.

The following are intentionally incomplete or deferred:

```text
non-associative comparison diagnostics in the AST builder
semantic validation and lowering of arbitrary postfix chains
semantic validation of type references
generic value arguments such as fixed-point scales
pointer/reference source syntax and semantics
semantic name resolution
type checking
graph IR lowering
runtime execution semantics
provider/capability resolution
```

The current expression tree is precedence-aware for the established arithmetic
and comparison operators. Recognized children are populated recursively,
parentheses control grouping without producing synthetic AST nodes, and postfix
call/index/field expressions bind above binary operators. Postfix expressions
compose uniformly: calls own their callee/base as child zero followed by their
arguments, indexes own their base as child zero followed by their index
expressions, and field access owns its base as child zero. Chained postfix forms
therefore nest instead of flattening source spelling into a named-call special
case.

Each expression now has one canonical typed payload. Structural roles such as
binary `left`/`right`, postfix `base`, call `arguments`, index `indexes`, list
`elements`, and record `fields` are stored only in that payload. The JSON
`kind`, summary `text`, and `child_expressions` fields remain available as
derived compatibility projections; they are not independently mutable AST
state.

Canonicalization also repaired one previously hidden classification error:
`3.14` is now one `FloatLiteralExpr` with text `"3.14"`, rather than an
`IntegerLiteralExpr` containing only the leading `"3"` token.

Type references now follow the same canonical-payload rule as expressions.
`NamedTypeRef` owns qualified-name segments, `GenericTypeRef` owns its
constructor segments and nested type arguments, and `ArrayTypeRef` owns one
immutable element type plus ordered source extents. Generic `kind` and rendered
type strings remain as derived JSON compatibility projections; they are not
independent AST state.

Here, canonical payload means the single authoritative AST representation. It
does not mean that semantic analysis has resolved the written reference to a
canonical type identity. The raw AST preserves spellings such as `Bool`, `bool`,
`int`, and `int64` distinctly. Their binding classification is documented in
[`docs/flowmini/v0.24-type-policy.md`](../../../docs/flowmini/v0.24-type-policy.md).

The C4 boundary deliberately excludes pointer and reference AST forms. ABI
pointer-shaped contracts remain ordinary named semantic types such as
`c_string`; backend representation does not leak into source syntax. Pointer
and reference forms require a separate design of ownership, mutability,
lifetime, aliasing, ABI, and safety semantics before they can honestly join the
language.

Canonical type parsing also repairs two old boundary errors. Generic and array
initializers now attach to their actual typed binding rather than disappearing
after a one-token type parse. Function signatures using `-> Type` now expose
their return type and following body instead of leaving the function falsely
bodyless.

Example:

```flow
x + 1
```

is recognized as a binary expression with operator `"+"`, with recursively
populated operands. Mixed arithmetic and comparison expressions now follow the
same precedence contract as the established Flowmini frontend.

This is intentional.

v0.24 follows the rule:

```text
First existence.
Then visibility.
Then population.
Then dependency.
```

## Golden AST regression tests

The canonical AST source examples live in:

```text
examples/ast/*_probe.flow
```

The expected normalized AST JSON outputs live in:

```text
tests/expected/ast/*.ast.json
```

The golden AST test runner is:

```text
tools/run-flowmini-ast-golden-tests.sh
```

Every generated AST is first checked by:

```text
tools/validate-flowmini-ast-payloads.py
```

The validator requires a canonical declaration arena with stable positional
IDs, exactly one source-unit structural parent, and agreement with derived
declaration projections. It also requires complete expression and type-reference payload shapes,
valid expression references, source locations, and exact agreement between
canonical payload roles and their generic compatibility projections. For
statements, it also requires exact payload fields, valid source forms and
assignable targets, structural block references, and agreement with legacy
statement projections.

The CMake target is:

```bash
cmake --build cmake-build-debug --target flowmini_ast_golden_tests
cmake --build cmake-build-debug --target flowmini_frontend_bundle_tests
```

The expected result is:

```text
AST golden tests: PASS (26)
Symbol projection tests: PASS (11/11)
Frontend bundle tests: PASS (5 golden, 1 isolated, 11 negative)
```

The full Flowmini suite remains:

```bash
cmake --build cmake-build-debug --target flowmini_suite
```

Expected result:

```text
total: 78
pass:  78
bad:   0
```

## Golden update mode

When AST output changes intentionally, update goldens with:

```bash
FLOWMINI_UPDATE_AST_GOLDENS=1 tools/run-flowmini-ast-golden-tests.sh
```

Then inspect the diff before committing:

```bash
git diff -- tests/expected/ast/
```

Golden files should only be updated intentionally.

The design law is:

```text
If v0.24 AST behavior changes,
the golden AST tests must either fail
or the expected AST files must be intentionally updated.
```

## Current main rule

v0.24 supports exactly one root `main` block in a root program.

Multiple root `main` blocks are currently an error.

Future Flowmini/Flowcore may support multiple named buildable or runnable targets from the same source base using a model like:

```flow
program toolset

target cli {
    main {
        ...
    }
}

target daemon {
    main {
        ...
    }
}
```

That future direction is documented in:

```text
docs/language/named-targets.md
```

It is not implemented in v0.24.
