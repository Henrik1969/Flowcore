## Architectural stack

Current conceptual stack:

```text
Lexer
    Here are the words/symbols.

TokenTree
    Here are the words/symbols grouped by source structure.

Flowmini AST
    Here is what the program says.

Semantic checker
    Here is whether what it says is legal.

SymbolTable
    Here are the named facts/scopes/contracts.

Graph IR
    Here is the executable/source architecture as nodes, ports, wires.

Lowerer/runtime
    Here is how we actually make it run.
```

Important distinction:

```text

```

## Current expression capabilities

The AST can now represent the following shallow expression structures.

### Calls

```flow
square(x)
```

Current AST meaning:

```text
call expression
    text = "square"
    child_expressions = argument expressions
```

### Unary expressions

```flow
-x
```

Current AST meaning:

```text
unary expression
    text = "-"
    child_expressions = operand expression
```

Important rule fixed during A3:

```text
leading "-" at expression start is unary
"-" after a left expression is binary
```

### Binary expressions

```flow
x + 1
```

Current AST meaning:

```text
binary expression
    text = operator
    child_expressions = lhs expression, rhs expression
```

This is recursively populated for current probe shapes. Full parser-quality associativity and all expression forms remain future work.

### Index expressions

```flow
arr[i]
```

Current AST meaning:

```text
index expression
    text = "arr"
    child_expressions = base expression, index expression
```

### Field access expressions

```flow
p.x
```

Current AST meaning:

```text
field_access expression
    text = "p.x"
    child_expressions = base expression
```

The field name is represented in the field-access payload while the base expression is linked structurally.

### List literals

```flow
[1, 2, 3]
```

Current AST meaning:

```text
list_literal expression
    text = "["
    child_expressions = element expressions
```

### Record literals

```flow
{x: 10, y: 20}
```

Current AST meaning:

```text
record_literal expression
    text = "{"
    child_expressions = field value expressions
```

Field names are not yet modeled as structural AST payloads.

## Known limitation: shallow child nodes

Child expressions are currently created shallowly.

Example:

```flow
square(x + 1)
```

May produce:

```text
call square
    child = binary "+"
```

But the binary child may not yet recursively contain its own `x` and `1` children depending on the path that produced it.

Recursive population is future work.

## Known limitation: binary precedence

Current binary expression handling is shallow.

Example:

```flow
a + b * c
```

The current AST should not yet be trusted as a proper precedence tree.

Future expression parser work must define:

```text
operator precedence
operator associativity
grouping behavior
unary/binary interaction
call/index/field binding strength
literal nesting
```

## Known limitation: record literals

Current record literals expose value expressions only.

Example:

```flow
{x: 10, y: 20}
```

Current structural meaning:

```text
record_literal
    children = 10, 20
```

The current model already includes name/value/location payloads. Future work may still refine this into richer field nodes:

```text
RecordLiteralField
    name
    value_expression
    location
```

## Current main/target rule

v0.24 currently supports exactly one root `main` block.

Multiple root `main` blocks remain an error.

Future language direction is named targets:

```flow
program toolset

target cli {
    main {
        ...
    }
}

target daemon {
    main {
        ...
    }
}
```

Canon law:

```text
A Flowcore program is a shared semantic universe.

A target is a named projection of that universe into a buildable or runnable product.

A main block is the entrypoint of a target.

For v0.24, root programs support exactly one main block.

Future versions may support named target scopes, each owning exactly one main block.
```

This is documented in:

```text
docs/language/named-targets.md
```

### Road C4: type-reference deepening

Purpose:

```text
Turn type references into real AST structures.
```

Needed:

```text
generic types
array types
reference/pointer types if kept
qualified names
function types later if desired
```

Status: complete for the honest v0.24 source forms.

Implemented:

```text
canonical NamedTypeRef payloads with qualified-name segments
canonical GenericTypeRef payloads with recursive type arguments
canonical ArrayTypeRef payloads with element type and source extents

```

Deliberately deferred:

```text

```

ABI pointer-shaped contracts remain named semantic types. Pointer/reference
syntax must not be added until ownership, mutability, lifetime, aliasing, ABI,
and safety semantics have been designed explicitly.

### Road C5: statement deepening

Purpose:

```text
Give statements stronger expression ownership and richer structure.
```

Status: in progress.

Completed:

```text
C5.1 canonical return value-expression ownership
C5.1 return expression_ids compatibility projection derived from that ownership
C5.1 unified function/main/nested statement-body parsing
C5.1 direct and nested return regression coverage
C5.2 canonical typed-binding initializer-expression ownership
C5.2 typed-binding expression_ids compatibility projection derived from that ownership
C5.2 empty initializer parentheses remain structural and do not fabricate expressions
C5.2 direct and nested typed-binding regression coverage
C5.3 canonical plain-assignment value-expression ownership
C5.3 plain-assignment expression_ids compatibility projection derived from that ownership
C5.3 function, nested, and main-body assignment regression coverage
C5.4 canonical if/while condition-expression ownership
C5.4 if/while expression_ids compatibility projection derived from that ownership
C5.4 function, nested, and main-body condition regression coverage
C5.5 optional else branch owned directly by If
C5.5 nested else-body statement population
C5.5 no synthetic else branch when source omits else
C5.5 nested if/else regression coverage
```

Current law:

```text
A statement owns expressions according to their semantic role.
Generic expression lists may remain as compatibility projections during the
migration, but they are not the canonical meaning of a migrated statement role.

For typed bindings, empty `()` remains meaningful structural syntax but does
not manufacture a fake initializer expression. Canonical initializer ownership
exists only when an actual expression is present.

For C5.3, the currently supported plain assignment form keeps its identifier
target in `name` and canonically owns only the right-hand-side value expression.
Generalized assignment targets such as field/index lvalues remain a separate
future AST design problem rather than being implied by this migration.

For C5.4, `if` and `while` canonically own a `condition_expression`. The legacy
`has_condition` and `expression_ids` JSON fields remain derived compatibility
projections.

For C5.5, `else` is not a standalone statement kind. It is an optional branch
owned by the immediately preceding `if`. The existing `body` remains the true
branch; `else_body` is present only when the source contains an explicit
`else { ... }`. No synthetic empty false branch is created. `else if` sugar
remains deliberately outside the C5.5 boundary; equivalent nested structure can
already be expressed as an `if` inside `else_body`.
```

Remaining:

```text
expression statements
flow statements if retained
```
